# FPV-каталог: Telegram + Immich

Rust-сервис индексирует видео в серверной папке, даёт пилотам поиск и ежедневные уведомления, отправляет небольшие файлы через Telegram. Большие файлы публикуются через external library уже установленного Immich. Данные каталога, права, очереди и история уведомлений хранятся в PostgreSQL.

## Запуск на Debian

1. Скопировать `.env.example` в `.env`. Заполнить Telegram Bot Token, положительный Telegram ID главного администратора, серверный `VIDEO_ROOT`, данные Immich и пароль PostgreSQL. Пароль в `DATABASE_URL` должен совпадать с `POSTGRES_PASSWORD` (спецсимволы в URL кодируются percent-encoding).
2. Убедиться, что UID/GID приложения может читать папку и входить во все каталоги. По умолчанию контейнер работает как `10001:10001`; `APP_GID` можно задать как группу с доступом к архиву.
3. Настроить Immich по разделу ниже. Immich использует отдельный существующий стек; его PostgreSQL и Redis не заменяются компонентами этого проекта.
4. Загрузить готовый образ, собранный на рабочей станции или в GitHub Actions (см. ниже). Первый запуск делать с `DELIVERY_ENABLED=false`, `NOTIFICATIONS_ENABLED=false`. Выполнить `docker compose up -d --no-build`. Миграции запускаются автоматически; bootstrap-администратор создаётся идемпотентно.
5. В Telegram открыть `/start`, заполнить справочники, запустить `/scan`, проверить `/status` и `/search`. После проверки включить выдачу и уведомления в `.env`, затем `docker compose up -d`.

Порт приложения публикуется только на localhost. `/healthz` проверяет PostgreSQL. Для fallback настроить HTTPS reverse proxy по примеру в `deploy/Caddyfile.example`. Immich может быть доступен приложению по LAN; в `IMMICH_PUBLIC_URL` нужен адрес, открывающийся с телефона пользователя. `IMMICH_BASE_URL` содержит `/api`, публичный URL его не содержит. `localhost` внутри контейнера приложения не означает сервер Immich.

```sh
docker compose logs --tail=100 fpv-catalog
docker compose run --rm fpv-catalog --scan-once
docker compose run --rm fpv-catalog --immich-check
```

Секреты не коммитятся. Поддерживаются `IMMICH_API_KEY_FILE` и `TELEGRAM_BOT_TOKEN_FILE`: вместо переменной с ключом можно смонтировать Docker Secret и указать путь к нему. Не сохраняйте вывод `docker compose config` с реальными секретами в файлы репозитория.

## Сборка вне Orange Pi

На Orange Pi сборки запрещены: основной Compose содержит только готовый image и никогда не собирает приложение. На сервер передаётся образ для `linux/arm64`, затем выполняются `docker load` и `docker compose up -d --no-build`. Тег задаётся через `FPV_CATALOG_IMAGE`; по умолчанию — `fpv-dvr-organaiser-fpv-catalog:latest`.

В GitHub Actions вручную запустить **ARM64 deployment image** на нужной ветке. Workflow собирает образ на ARM64 runner GitHub и сохраняет artifact `fpv-catalog-arm64`. После скачивания и распаковки artifact передать содержащийся в нём tar.gz на сервер:

```sh
scp fpv-catalog-arm64.tar.gz orangepi:/tmp/
ssh orangepi 'docker load -i /tmp/fpv-catalog-arm64.tar.gz'
ssh orangepi 'cd ~/fpv-dvr-organaiser && docker compose up -d --no-build'
```

Workflow доступен после отправки ветки в GitHub; ручной запуск из UI требует наличия workflow в default branch. ARM runner должен быть доступен для репозитория и тарифного плана. Секреты бота и доступ по SSH в GitHub передавать не требуется: workflow только собирает artifact, развёртывание выполняется отдельно.

На рабочей станции с нужной архитектурой можно выполнить `docker compose -f docker-compose.yml -f docker-compose.build.yml build fpv-catalog`, затем `docker save fpv-dvr-organaiser-fpv-catalog:latest | gzip > fpv-catalog-arm64.tar.gz`. На x86 для ARM64 нужен cross-build: бинарник, собранный под `aarch64-unknown-linux-gnu` с sysroot Debian Bookworm, упаковывается через `deploy/Dockerfile.prebuilt` на рабочей станции с поддержкой ARM64-образов. Если проверенный ARM64 runtime уже есть локально, `deploy/Dockerfile.update` заменяет в нём бинарник без выполнения ARM-кода. Этот вариант не обновляет пакеты базового образа; для их обновления нужна полная сборка на ARM runner или с эмуляцией. Проверять архитектуру образа перед переносом; AMD64-образ на Orange Pi не запускается.

## Immich

В существующий compose Immich добавить read-only mount по примеру `deploy/immich.compose.override.example.yml`; выполнить обновление этого стека. При отдельном worker-контейнере тот же каталог должен быть подключён и туда.

Администратор Immich создаёт отдельного обычного пользователя `fpv-bot`, затем **external library с этим пользователем как владельцем** и import path `/mnt/fpv`. Владельца библиотеки потом изменить нельзя. Установить расписание сканирования `*/15 * * * *`; experimental filesystem watcher для работы бота не требуется. 15 минут — интервал запуска, а не гарантия времени завершения большого сканирования/транскодирования.

Исключить служебные каталоги: `**/.video-sync/**`, `**/.rsync-partial/**`, `**/.DS_Store`, `**/._*`. Не подключать архив как `UPLOAD_LOCATION`. Каталог должен быть доступен только на чтение и Immich, и боту.

У технического пользователя создать API key с permissions:

- `asset.read`
- `sharedLink.create`
- `sharedLink.read`
- `sharedLink.delete`

Записать ключ и UUID библиотеки в `.env`. Бот использует `/search/metadata` с `filter.originalPath.eq`, cursor pagination и проверяет точный путь, library ID, тип VIDEO, offline/trash. Он не читает БД Immich, не загружает вторую копию и не управляет библиотеками через административный API. Ключ без доступа к библиотеке не сможет найти assets.

После индексации отдельного тестового видео выполнить:

```sh
docker compose run --rm fpv-catalog --immich-smoke 'test_14.10.26/t1_o4/testpilot/test.mp4'
```

Это создаёт временную публичную ссылку только на указанный тестовый asset и сразу отзывает её. Затем проверить настоящую выдачу через бота, проигрывание и скачивание оригинала, read-only mount. Без адреса/ключа реального Immich контрактные тесты не подтверждают совместимость вашего экземпляра.

Для полного HTTP smoke на сервере: `python3 deploy/smoke_immich.py 'событие/аппарат_система/видео.MP4'`. Скрипт читает `.env`, временно публикует ровно этот файл на 5 минут, проверяет публичную страницу, состав и флаги ссылки, сравнивает первые 1024 байта скачанного оригинала с исходником, отзывает ссылку и проверяет отказ в доступе. Ключи и URL ссылки в вывод не попадают. Использовать файл, который разрешено публиковать для такой проверки.

Для обновлений используется стабильный release-канал Immich; образ обновляется вручную до текущей версии после чтения release notes и smoke-теста. API-контракт этого клиента требует нового `filter`/`orderBy` и `nextCursor` из опубликованной OpenAPI-схемы (v3.2+). Старые версии с legacy pagination не поддерживаются. На неожиданной схеме клиент возвращает ошибку и не публикует непроверенный asset.

Официальные источники: [external libraries](https://docs.immich.app/features/libraries/), [sharing](https://docs.immich.app/features/sharing/), [OpenAPI](https://docs.immich.app/openapi.json).

## Доставка и готовность файлов

Файлы остаются на прежних путях. Бот не пишет в папку видео и не удаляет оригиналы. По умолчанию `REQUIRE_SYNC_RECEIPTS=true`: импорт нового файла допускается после сверки с SHA-256 receipt, атомарно записанным серверным sync-helper после проверки передачи.

Поддерживаются подтверждения существующего sync-helper `VIDEO_ROOT/.video-sync/<id>.receipt.json` и JSON-файлы внутри `VIDEO_ROOT/.video-sync/receipts/` с произвольным уникальным именем. Файлы `*.intent.json` не являются подтверждениями и игнорируются. Содержимое receipt:

```json
{
  "relative_path": "ugor_19.09.26/t1_o4pro/kostyanbtw/video.MP4",
  "size_bytes": 123456789,
  "sha256": "64 hex characters of the verified file SHA-256"
}
```

Дополнительные поля (`verified_at`, версия протокола) допускаются. Receipt должен быть записан через rename временного файла после подтверждения SHA-256. Сам отправитель описан в `MAC_VIDEO_SYNC_PLAN.md`; исходников отправителя здесь нет. Этот конкретный формат нужно использовать в его helper. Наличие конечного имени rsync не заменяет receipt.

Для предварительно проверенного старого архива можно явно поставить `REQUIRE_SYNC_RECEIPTS=false`. В этом режиме нужен договор: полностью скопированные видео перемещаются в корень атомарно и далее не меняются. `STABLE_SECONDS=60` — дополнительная проверка стабильности метаданных, она не доказывает окончание длительного копирования.

Сканер не следует symlink, отсеивает служебные каталоги, вызывает ffprobe только при первом импорте. Размер, mtime и сведения медиа кэшируются; изменение уже принятого файла по прежнему пути вызывает `conflict`. Для принятия замены требуется новое имя. Пропавшие видео отмечаются `missing`. Полная SHA-256-проверка неизменившихся файлов на каждом проходе не выполняется; изменение содержимого с сохранением размера/mtime остаётся задачей полной проверки sync-helper.

Поддерживается `событие/аппарат_система[_colored]/пилот/файл` и `событие/аппарат_система[_colored]/файл`. Во втором случае нужен `/defaultuser ID` (внутренний ID каталога). `/defaultuser none` отключает пользователя по умолчанию. Имена сравниваются после NFKC и приведения к нижнему регистру; поддерживаются aliases с `_`. Несколько совпадений не разрешаются догадкой.

Дата события может отсутствовать. Разбираются DD.MM.YY, DD.MM.YYYY, MM.YY, MM.YYYY и YYYY; YY означает 20YY. Месяц/год хранится интервалом, фильтр использует его пересечение с запросом. Неизвестная дата исключается только при активном фильтре по датам. Ручная дата не перезаписывается сканированием.

## Использование бота

Бот работает в личных чатах. Неизвестный пользователь через `/start` подаёт заявку, но не получает каталог. Администратор добавляет пилотов через «Управление» → «Добавить пользователя» или `/adduser`. Необработанные заявки доступны там же как кнопки с именами. Отклонить заявку можно через `/reject TELEGRAM_ID`. Главного администратора из конфигурации нельзя удалить или понизить.

`/start` и `/menu` показывают постоянную клавиатуру внизу чата: поиск видео, фильтры, подписки, уведомления, мои запросы и помощь. Клавиатура не скрывается после нажатия. Администратору доступна кнопка «Управление» с состоянием, сканированием, справочниками и добавлением пользователя; «Главное меню» возвращает основную клавиатуру. Поиск с клавиатуры сохраняет текущие фильтры. Выбор конкретного видео и подтверждение выдачи остаются кнопками под сообщениями.

В «Фильтрах» аппараты, видеосистемы и пилоты выбираются отметками ✅: можно выбрать сразу несколько значений, повторное нажатие снимает отметку. Пустой выбор означает «любые». Внутри категории подходит любой отмеченный вариант, а разные категории применяются вместе: например, (T1 или Microsector) и N3. «Готово · К фильтрам» возвращает обзор с выбранными названиями, «Показать видео» открывает результаты. Длинные справочники разбиты на страницы, отметки между страницами сохраняются. «Любые — сбросить этот фильтр» очищает только текущую категорию. «Сбросить все фильтры» доступно и в обзоре, и прямо в результатах; сбрасывает также даты, текст и номер страницы. OSD и цветокоррекция переключаются между «любые / есть / нет» с отображением текущего значения. Для введённых дат и текста в обзоре есть отдельные кнопки сброса.

Добавление пользователя проходит без JSON: Telegram ID → ФИО → ник → ник Telegram → имена папок через запятую → роль → публичность видео → проверка и сохранение. Необязательные поля можно пропустить. Кнопки «Назад» и «Отмена» доступны на каждом шаге; `/cancel` отменяет форму. `/user 1004106925` начинает тот же диалог с заполненным ID. До подтверждения пользователь не создаётся. Должны быть указаны ID и хотя бы одно имя или имя папки. По умолчанию выбраны роль пилота и публичные видео; оба параметра явно подтверждаются кнопками. «Пользователи» показывает читаемые карточки с кнопкой редактирования. Кнопки старых шагов и повторное сохранение отклоняются. Незавершённые формы хранятся в памяти и сбрасываются при перезапуске бота.

Списки справочников, параметры поиска, прогресс выдачи и состояние каталога показывают русские подписи вместо JSON и внутренних кодов. Подробности технических ошибок остаются в журнале сервиса.

Шаги добавления/редактирования, поиск с фильтрами и страницами, подписки и уведомления обновляют свои управляющие сообщения вместо отправки новых на каждом нажатии. При открытии поиска, фильтров, подписок или уведомлений с нижней клавиатуры либо соответствующей командой раздел появляется новым сообщением внизу чата; прежнее управляющее сообщение удаляется только после успешной отправки нового. Дальнейшие действия кнопками под сообщением обновляют его на месте. Текстовые ответы формы и команды навигации после обработки удаляются. Ошибки ввода появляются в текущем шаге, ошибки нажатия — во всплывающем уведомлении. При сохранении итоговая карточка остаётся в истории; новая форма создаёт отдельное сообщение. Карточки видео и пользователей, запрошенная справочная информация, ссылки, видео и документы не входят в список управляющих сообщений и не удаляются этой очисткой. В карточке видео есть «✕ Закрыть»: она удаляет только эту карточку по явному нажатию, не отменяя уже запущенную выдачу. Для остановки выдачи используется отдельная кнопка «Остановить» в запросе. Старые сообщения до обновления автоматически не очищаются. Если управляющее сообщение удалено вручную или больше не редактируется, бот создаёт новое; сетевой сбой не приводит к созданию дубликата. Учёт этих сообщений хранится в памяти и начинается заново после перезапуска.

В подписках нажатие на пилота включает или выключает только его подписку, сохраняя даты остальных подписок. В уведомлениях кнопками можно включить/выключить дайджест и выбрать 06:00, 08:00, 10:00, 12:00, 18:00 или 21:00 по Москве. Для другого времени остаётся `/notify ЧЧ:ММ`.

Поиск и выдача управляются кнопками. Также доступны команды:

| Действие | Команда |
|---|---|
| Поиск по тексту | `/search karelia` |
| Фильтры | `/search {"from":"2026-08-17","to":"2026-08-17","device":[1,2],"system":[2],"osd":false,"colored":true,"pilot":[3,4]}` |
| Следующая / предыдущая страница | `/next`, `/prev` |
| Карточка видео | `/info VIDEO_ID` |
| Выбрать способ выдачи | `/video ID`, `/document ID`, `/link ID` |
| Вся текущая выборка | `/all video`, `/all document`, `/all immich` |
| Подтвердить / контролировать | `/confirm`, `/jobs`, `/cancel UUID` |
| Выбрать пилотов для дайджестов | `/subscribe ID ID` или `/subscribe none` |
| Время по Москве | `/notify 08:00`, `/notify on`, `/notify off` |

Результаты показывают общее число, размер и по 10 видео на страницу, с номером вида «Страница 1 из 2». Кнопки «Предыдущая» и «Следующая» появляются только при наличии соответствующей страницы. Устаревший переход, завышенный номер в JSON или уменьшение каталога возвращают к последней доступной странице; пустая выборка не имеет кнопок перелистывания. Карточка содержит ID события, аппарат, пилота, систему/OSD, цветокоррекцию, длительность, разрешение, FPS и размер. У обычного пилота видны его собственные видео и видео активных публичных пилотов; у администратора — все классифицированные видео. Доступ повторно проверяется при выдаче и на fallback endpoint.

Администрирование выполняется типизированными JSON-командами с проверкой обязательных полей:

```text
/device {"name":"T1","type":"quad","aliases":["t1","trainer1"]}
/system {"name":"O4 Pro","with_osd":false,"aliases":["o4pro"]}
/user {"telegram_id":123456,"nickname":"Kostyan","aliases":["kostyanbtw"],"is_public":true}
```

Для редактирования добавить `"id":ID`: команда заменяет поля и aliases, сохраняя историю видео. `type` — `plane/quad/other`, `with_osd` обязателен. При отсутствии aliases пилота используются заполненные ФИО, ник и Telegram username. Допустимо добавить пилота только с Telegram ID и хотя бы одним alias.

`/list users`, `/list devices`, `/list systems` показывают внутренние ID. `/delete user ID`, `/delete device ID`, `/delete system ID` деактивируют записи. `/scan` вручную запускает проход; изменения справочников запускают переклассификацию автоматически и повторяются периодическим сканером. `/date EVENT_ID YYYY-MM-DD YYYY-MM-DD` задаёт ручной интервал события. `/status` показывает состояния видео и очередей, нерешённые проблемы классификации, ошибки файлов и системные проблемы. `/alertinterval 0|15|60|1440` задаёт интервал системных уведомлений в минутах.

## Очереди и ссылки

Выбранный набор подтверждается с количеством и размером; его состав фиксируется в БД. Telegram-предел по умолчанию 49 000 000 байт. Бот не перекодирует оригиналы для Telegram: совместимый небольшой MP4 отправляется как video, прочие форматы можно выбрать как document. Большие файлы автоматически идут в Immich; также можно явно выбрать Immich для всего набора.

`TELEGRAM_UPLOAD_TIMEOUT=10m` задаёт общий тайм-аут отправки файла, включая загрузку по медленному каналу. Для сообщений и long polling сохраняются обычные настройки клиента; загрузка выполняется отдельной фоновой задачей и не блокирует команды бота.

Бот ждёт asset с backoff с первой неудачной попытки до `IMMICH_ASSET_WAIT_TIMEOUT=30m`, сохраняет прогресс и продолжает после рестарта. Набор разбивается по `IMMICH_SHARE_CHUNK_SIZE=500`. Каждая ссылка — `INDIVIDUAL`, download разрешён, upload запрещён, TTL по умолчанию 7 дней. Показ метаданных задаётся `IMMICH_SHOW_METADATA` (по умолчанию `false`). **В Immich 3.2.2 и 3.3.3 для скачивания оригинала необходимо явно поставить `IMMICH_SHOW_METADATA=true`**: при скрытых метаданных сервер принудительно запрещает скачивание, даже если запрос содержит `allowDownload=true`. Это поведение подтверждено живым тестом и [исходниками Immich 3.3.3](https://github.com/immich-app/immich/blob/v3.3.3/server/src/services/shared-link.service.ts#L101). Владелец архива должен разрешить показ метаданных перед включением этой настройки.

Бот проверяет фактически возвращённые flags, срок и точный набор assets. Несоответствующая ссылка отзывается и не отправляется пользователю. Потерянный ответ POST восстанавливается по уникальному описанию запроса и точному набору assets. Истёкшие или отозванные ссылки удаляются через API отдельным фоновым процессом, работающим даже при выключенной выдаче.

Immich-ссылка открывается без аккаунта; доступ имеет любой, кому переслали URL. Связь с пользователем в каталоге нужна для аудита и отзыва, она не аутентифицирует посетителя страницы Immich. Изменение приватности/роли/активности инициирует отзыв затронутых ссылок. Смена Telegram ID пользователя отзывает его ссылки и отменяет его незавершённые запросы. При недоступности Immich отзыв повторяется; до его успешного выполнения удалённая ссылка может оставаться действующей. Скрытие metadata в UI не удаляет метаданные из скачиваемого оригинала.

`/fallback VIDEO_ID` доступен только активному администратору, выдаёт собственную случайную ссылку на 1 час при настроенном `FALLBACK_BASE_URL`. Токен в БД хранится как SHA-256, URL не раскрывает путь, скачивание поддерживает Range и заново проверяет роль/доступ. Обычным пользователям fallback автоматически не выдаётся.

Дайджесты — 08:00 по Москве по умолчанию, только впервые классифицированные видео выбранных пилотов, появившиеся после подписки. Администратор подписывается на всех при назначении, новый пилот добавляется администраторам; обычный пользователь начинает с себя. Изменённые вручную подписки не сбрасываются фоновыми задачами. `/notify off` отключает ежедневный дайджест; системные уведомления администратора управляются отдельно через `/alertinterval`. Ошибка отправки одному пользователю не блокирует остальных. При переиндексации повторного дайджеста нет.

Telegram не предоставляет идемпотентного sendMessage/sendVideo: если процесс аварийно завершится после отправки, но до фиксации в БД, возможно повторное сообщение. Выборка, asset-проверки, запись ссылок и прогресс сохраняются; абсолютная exactly-once-доставка сообщений не обещается.

## Обслуживание и проверки

Тесты рассчитаны на Rust stable и PostgreSQL 16. Контейнерный smoke-тест проверяет миграции и чтение duration/width/height через ffprobe из read-only архива. GitHub Actions настроен на fmt, clippy и весь набор тестов с отдельным PostgreSQL. Проверки реального развёртывания описаны в `deploy/ORANGEPI.md`.

```sh
cargo fmt --check
cargo clippy --locked --all-targets -- -D warnings
TEST_DATABASE_URL=postgres://postgres:password@localhost:5432/fpvtest cargo test --locked
```

Интеграционные тесты создают изолированные схемы и временные папки; требуют ffmpeg и тестового PostgreSQL. Без `TEST_DATABASE_URL` PostgreSQL-сценарии явно пропускаются. HTTP-тесты проверяют точное сопоставление Immich paths/library, флаги ссылки, ожидание asset, retry/timeout, batching, восстановление и отзыв; Telegram/Immich заменены mock-серверами.

Сканер и фоновые очереди используют PostgreSQL advisory locks. Запускайте один экземпляр Telegram long-polling бота: несколько pollers с одним токеном конфликтуют. Параметры фильтра и неподтверждённый выбор хранятся в памяти и после рестарта сбрасываются; подтверждённые jobs, подписки и уведомления сохраняются в PostgreSQL.

Резервная копия каталога:

```sh
docker compose exec -T postgres pg_dump -U fpv -d fpv -Fc > fpv-catalog.dump
```

Восстановление в отдельную чистую БД после остановки приложения:

```sh
docker compose stop fpv-catalog
docker compose exec -T postgres pg_restore -U fpv -d fpv --clean --if-exists < fpv-catalog.dump
docker compose up -d fpv-catalog
```

Хранить резервные копии в защищённом месте: в них есть Telegram IDs и ключи public links. Отдельно сохранять `.env`, данные/БД Immich и оригинальные видео; дамп каталога не содержит самих видео. Перед обновлением делать backup, запускать тесты, загрузить готовый образ, выполнить Immich smoke и `docker compose up -d --no-build`. На Orange Pi не собирать образы и бинарники. Не выполнять `docker compose down -v`: это удаляет данные PostgreSQL.
